Fixes Accessibility approval becoming stale after an update while System Settings still shows OpenLocker as enabled.

- Releases now reuse a persistent certificate-bound signing identity. A regression test changes and re-signs a binary, then checks it against the previous release's actual macOS designated requirement.
- The installer detects identity changes and guides users through a one-time approval renewal. Upgrading from 0.1.0 needs this renewal; subsequent releases signed with the same identity retain it, subject to macOS policy.
- One setup window replaces the repeated permission alert. **Repair approval** clears only OpenLocker's stale Accessibility entry and opens Settings. It never grants permission on the user's behalf. The window detects approval and continues the pending action automatically.
- Protected app settings are preserved. Failed repairs remain retryable; polling never resets permission. Signed release builds refuse ad-hoc fallback or an unexpected certificate.

Download the DMG, open **Install OpenLocker**, quit the old OpenLocker before installing, then open the installed app. If asked, choose **Repair approval & open Settings**, then enable OpenLocker. If it isn't listed, add the installed `~/Applications/OpenLocker.app` using **+**.

The release is **self-signed, not Apple-notarized**. It needs no paid developer account but macOS may still show a first-launch Gatekeeper warning. OpenLocker does not disable Gatekeeper or change system certificate trust.

Validation: extension tests, Swift lock/activation/approval tests, signed upgrade and installer tests, universal arm64/x86_64 builds, signature verification, and native-host protocol checks. Physical Touch ID and full end-to-end macOS permission migration still require user interaction; automated signature tests do not substitute for those checks.
